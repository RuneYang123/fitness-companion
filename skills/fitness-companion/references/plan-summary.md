# 流程结束时的计划总清单

用户选择整理最终清单、要求把本次全部安排放在一起，或明确采用整份计划时读取。所需模块刚看完，只提供下一步选择，不立即展开总清单。只汇总本次已经讨论的内容，不重新收集资料，不另拟一套计划，不读取私人旧方案补空缺。

## 先让用户选择

最后一个所需模块（例如睡眠）正常输出该模块的小结和建议即可。结尾可说：“还有哪一块不合适，我们可以先改那一块；或者先按这版执行，我再把完整清单整理给你。”措辞自然即可，不要求用户输入固定口令。

- 用户继续提出修改：只处理相关修改，再按上下文衔接，不提前展开总清单。
- 用户选择“给我最终清单”“把清单列出来”“先按这版执行”等：进入下面的最终交付，同一回复给总清单和原文结语，不额外索要一次确认。
- 用户只是回答睡眠、饮食等资料，或仍在选模块：继续当前步骤，不能当成已选择清单。
- “好的、可以”结合上下文理解，单纯认可当前建议不自动触发；明确是在答应整理最终清单时可以进入交付，不机械重问。
- 用户问今天练什么、某餐清单或单个模块：按当前请求处理，不把普通“清单”二字都理解为最终总清单。用户明确只要汇总、不加结语时照做。

## 怎么列

开头可以说“把这次的安排放在一起，后面照着看就行”。按训练、饮食、补剂、睡眠与恢复的顺序，只保留用户选择过的模块。是具体执行清单，不只是“每周三练、饮食均衡、注意恢复”这样的概述。

| 模块 | 总清单保留的内容 |
|---|---|
| 训练 | 每周或循环顺序、预计时长；具体关节活动与次数、低疲劳激活准备；每个训练日的全部当前动作、组次、一句提示和视频入口，仍按既定格式让视频另起一行；必要设置、休息、重量选择与进阶、有氧和恢复。只汇总已有安排，缺少起始公斤数时不猜 |
| 饮食 | 已经给过定量方案时，先列每日碳水、蛋白质、脂肪目标及可选总热量，再列每餐具体食品、份量、生熟重和必要点餐提示；原本只需要生活份量时沿用，不为做总清单新增热量计算。不默认加全天各食品克数汇总或长篇候选食物库 |
| 补剂 | 只列当前实际采用的项目与已确认用法；决定暂不使用时，明确写“目前不安排补剂”。尚未选择的蛋白粉、肌酸等不写成每天要吃，也不重发完整候选库 |
| 睡眠与恢复 | 已知作息、白天状态及商定的少数调整；睡眠窗口与实际时长分清，当前情况与建议目标分清，不凭总清单补造新时间 |

训练按训练日分短表、饮食按餐次分表，补剂与恢复可各用一两句话。保留执行与安全所需信息；不重新解释理论、复述整份个人档案或展开动作详解。已讨论的停止条件、必要来源或教学链接不因汇总而丢失。

沿用本次最新的明确修改。临时替换标清适用范围，不当成长期更改；计划安排不写成已经完成。只有部分资料时标清相关缺项，不从示例套数值。总清单只汇总已有建议，不借此把未采用的产品、备选动作或额外有氧加进来。

## 最终交付的顺序

- 用户选择最终清单或明确采用整份计划后：在同一回复中先列最终总清单，必要时简短提供一次[接续记录](continuation.md)选项，最后完整使用[作者结尾](plan-closing.md)。作者原文和P.S.不润色，不在结语后重新要求选择模块或确认。
- 日常查动作、反馈或局部修改：只给当前所需内容，不重复总清单和长结尾。只看部分模块也可以完成流程，不强迫补齐所有模块。

总清单默认在聊天中交付，不自动生成健康档案或保存文件。它不是跨聊天接续记录；用户希望带走并接着用时，再按接续规则补上日期、最近实际反馈和待确认项。保存文件仍先说明内容与位置，按用户选择进行，不写进公开Skill或GitHub仓库。
